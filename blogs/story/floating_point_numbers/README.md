# 为什么 0.1 + 0.2 不等于 0.3？

如果我们在 Python 中计算 `0.1 + 0.2`，可能会看到一个出人意料的结果：

```python
print(0.1 + 0.2)
```

输出结果为：

```text
0.30000000000000004
```

这不是 Python 算错了，而是计算机使用二进制表示小数时产生了近似误差。

## 从十进制到二进制

计算机无法用有限位二进制数精确表示十进制的 `0.1`。它只能保存一个非常接近
`0.1` 的数值，转换过程可以用下图表示：

![0.1 转换为二进制浮点数的过程](img/floating_point_conversion.svg)

例如，下面这些小数可以被二进制精确表示：

- `0.5 = 1/2`
- `0.25 = 1/4`
- `0.125 = 1/8`

但是，`0.1` 转换为二进制后会无限循环：

```text
0.00011001100110011...₂
```

由于计算机的存储空间有限，它必须在某一位进行舍入。因此，计算机实际保存的
不是精确的 `0.1`，而是一个非常接近它的数。

## 为什么 0.5 可以精确表示，而 0.4 只是看起来正常

`0.1`、`0.2` 和 `0.3` 的二进制展开都包含周期性的 `0011`，但起始位置不同，
因此存储时都会被舍入。两个已经存储的近似值相加后，精确和恰好位于两个相邻
可表示数的中点；按照“舍入到最近，遇到中点取偶数”的规则，结果选择了较大的
那个数，于是得到 `0.30000000000000004`。

作为对照，`0.5 = 2⁻¹`，可以被二进制精确表示。`0.4` 本身仍然是近似值，
但 `0.2 + 0.2` 恰好得到与字面量 `0.4` 相同的浮点数，所以比较结果为 `True`。

![0.1 + 0.2 ≠ 0.3、0.4 侥幸相等、0.5 真正精确的对比流程](img/floating_point_binary64.svg)

## 那么如何比较浮点数

程序中通常不应直接使用 `==` 判断两个计算所得的浮点数是否相等。Python 可以
使用 `math.isclose()` 判断它们是否足够接近：

```python
import math

result = math.isclose(0.1 + 0.2, 0.3)
print(result)
```

输出结果为：

```text
True
```

`math.isclose()` 使用相对容差和绝对容差判断两个数是否接近。默认参数适合许多普通
场景，但在科学计算或工程程序中，仍应根据数值范围和允许误差选择合适的容差。

## 浮点误差什么时候值得注意

假设游戏角色的位置每一帧增加 `0.1`。如果程序一直等待位置与目标值完全相等，
累积误差可能使这个条件始终无法成立。此时应判断角色是否已经越过目标，或者使用
允许一定误差的比较方式。

金额计算则更强调十进制结果的准确性。程序可以用整数记录“分”，也可以使用
`Decimal`。创建 `Decimal` 时最好传入字符串，避免先产生二进制浮点误差：

```python
from decimal import Decimal

total = Decimal("0.1") + Decimal("0.2")
print(total)
```

输出结果为：

```text
0.3
```

## 小结

浮点数是在计算速度、表示范围和存储空间之间作出的工程折中。了解近似误差后，
我们就能根据实际需求选择合适的比较方式或使用 `Decimal` 等精确十进制工具。
